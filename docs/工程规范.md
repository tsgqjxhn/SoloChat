# SoloChat 工程规范（v0.4）

这份规范约束「怎么改」，不解释产品功能。产品说明见 `README.md`，本轮审计与缺陷见 `docs/审计-v0.4.md`。

## 1. 架构与不可破坏的边界

- **运行时**：一个 `index.html`（CSS / JS / SVG / 协议 / 渲染全内联），双击即用。
- **桌面宿主**：`host/Program.cs` 提供 WebView2 窗口、文件访问、命令执行、运行时安装、桥接网络。页面通过 `postMessage` 文本协议调用宿主。
- **发布形态**：单个 `dist/SoloChatHost.exe`，页面与托管依赖全部内嵌；不产生散落 DLL / config。
- **零依赖**：不引入 npm 包、CDN、外部字体、远程脚本。运行时不联网取资源（用户主动发起的模型/搜索/网页请求除外）。
- **数据**：会话与产物在 IndexedDB + localStorage；密钥在宿主 DPAPI 保险库；不写遥测、不上传。

任何改动如果破坏以上任一条，必须先改这份规范并说明理由，不能悄悄绕过。

## 2. 体积与行数闸门

| 项 | 上限 | 当前（2026-11-06 v0.4.0） |
|---|---|---|
| `index.html` 字节数 | **1,048,576** | 1,008,183（余量 40 KB） |
| `index.html` 行数 | **18,000**（软上限） | 16,781 |
| 单个内联 `<script>` 语法 | 必须全部通过 `new Function` | 2 个脚本，通过 |
| `host/Program.cs` 行数 | 4,000（软上限） | 3,211 |

说明：README 早期写的「≤ 12,000 行」已不现实；行数不是可读性的有效代理，字节数才是发布形态的硬约束。余量低于 20 KB 时必须先做「抽出常量/目录数据」而不是继续加功能。

## 3. 标准开发流程

1. **找问题**：读代码 / 跑真实路径 / 看控制台，每条结论必须能指到函数或行号；「看起来不对」不算。
2. **写规格**：在 `docs/` 下写清现象、证据、期望行为、验收方式；一条一个编号。
3. **实现**：交给编码代理按规格改；一次只改一个主题，避免顺手重构。
4. **验证**：静态检查 + 构建 + 浏览器真实路径；不能验证的写明「未验证」，不许写成「已完成」。
5. **提交**：一个主题一个 commit，消息写「做了什么 + 版本号」；提交前 `git status` 必须只剩预期文件。
6. **发布**：`dotnet publish` → 校验 exe 版本 / 体积 → 更新 README 与变更记录 → 打 tag。

## 4. 前端代码约定

- 全部包在 IIFE 内，严格模式；ES5 语法（不使用可选链、`??`、`class`），保证 WebView2 旧内核也能跑。
- 新增模块用 `var X = (function(){ ... return {...}; })();`，对外只暴露必要方法。
- 注释只写「为什么」和不明显的边界；版本标记统一 `/* v0.4.x：… */`，不写日期与个人路径。
- DOM 只通过 `el()` / `$()` 创建与查询；用户/模型提供的内容一律 `textContent`，不拼 HTML。
- 所有网络请求走 `NET.raw` / `NET.send` / `fetchStream` / `bridgeStream`，不直接 `fetch`（否则代理、超时、CSP、协议适配全部绕过）。
- 所有会写盘/执行命令/花钱/对外发送的动作必须有确认或只读闸门；拦截要回注给模型，不能静默丢弃。

## 5. 配置字段约定（本轮 P0 的根因）

配置有两层：`S.cfg`（扁平镜像，界面与请求读它）与 `presets[]`（持久化实体）。**预置是唯一真源，扁平字段只能是它的镜像。**

新增连接字段时必须同时改四处：

1. `DEF_CFG` 默认值；
2. `loadCfg()` 从 `act` 镜像；
3. `mirrorPreset()` 写回扁平；
4. `setCfg()` 的连接字段白名单（`baseURL/apiKey/models/currentModel/provId/protocol/authType/chatPath/modelsPath/quirks`）。

新增普通配置（主题、开关、超时等）只需 `DEF_CFG` + `loadCfg` 默认合并 + UI 的 `data-cfg`。禁止只在 `setCfg()` 里写一次就当成持久化。

## 6. 新增一个内置工具，必须同时接五处

1. `EXT.BUILTIN` 登记（id / 标题 / 说明 / 可用模式）；
2. 围栏扫描 `FS.scan` 或 `WORK.scan` 的白名单；
3. 执行分支（`runReads` / `apply` / `WORK` 的 dispatch）；
4. 系统提示词中的工具清单（由 `EXT.prompt` 自动生成，确认模式过滤正确）；
5. 原生 tools schema（`toolSchemas()` 的白名单/关闭/本轮勾选过滤）。

只登记不执行 = 模型空等；只执行不登记 = 模型不知道；不进 schema = 开了原生调用就永远调不到。

## 7. 新增一个协议，必须同时接六处

1. `PROTOCOLS` 元数据（路径 / 版本头）；
2. `endpoint()` 的 URL 拼接（含 query key、api-version、Gemini 的 `:streamGenerateContent`）；
3. `authHeaders()` 的鉴权与额外头；
4. `convertBody()` 的请求体转换（system / 图片 / 文档 / tools / 思考字段）；
5. `createParserFor()` 的流事件 → `onDelta/onUsage`；
6. `parseNonStream()` 与 `fetchStream()` 的 JSON 兜底。

另加一条：默认关闭服务端留存（Responses 的 `store:false`），隐私优先。

## 8. 新增一个供应商目录条目

- 只填有把握的 `base` / `protocol` / `auth`；不确定的地址不要收录，或在 `docs/` 标注「未验证」。
- 带 `${ENV}` 占位符、带说明后缀、带多个候选 URL 的条目必须在加载时清洗，清洗后仍不合法就丢弃。
- 同一 Base URL 的重复条目按「首词不同 = 同一家」去重；区域/套餐档位（同首词）保留。
- 收录后至少验证：`endpoint()` 拼出的 chat/models URL 合理，`normBase()` 不会多补 `/v1`。

## 9. 验收清单（每次提交前）

- [ ] 内联脚本 `new Function` 全绿；
- [ ] `dotnet build host/SoloChatHost.csproj -c Release` 0 warning / 0 error；
- [ ] 干净 localStorage 打开首页无 console error；
- [ ] 演示模式可发消息、刷新后仍保留；
- [ ] 四个协议 `convertBody()` 探针无丢字段；
- [ ] 关闭/勾选工具后 `toolSchemas()` 与围栏白名单一致；
- [ ] 设置五个页面逐页打开无异常；
- [ ] 版本号 `APP_VER` = csproj = README；
- [ ] 体积 / 行数在上限内。

## 10. 已知架构债务

1. **单文件接近 1 MB**：新增功能会先撞字节上限。中期方案是把「常量 / 供应商目录 / 提示词 / SVG」抽到 `src/`，增加一个零依赖构建脚本把它们内联回 `index.html`；产物仍是单文件，源码可维护。未完成前，任何新功能都要先算字节预算。
2. **没有自动化浏览器回归**：目前靠 `SC_DBG` 钩子与人工冒烟。应补一个零依赖的 `tools/smoke.mjs`（Node + 本机 Edge/Chrome CDP），至少覆盖演示模式、协议转换、工具白名单。
3. **命令 / Python 无默认超时**：长任务可能永久占住工具链；需要默认上限与「停止即杀进程树」。
4. **配置双源**：本轮先做镜像同步；彻底方案是删掉扁平镜像，所有读写走 `AP()`，但那是一次大改，需单独评估。

## 11. 版本与发布

- 版本号唯一来源：`index.html` 的 `APP_VER`；csproj 的 `Version/AssemblyVersion/FileVersion/InformationalVersion` 必须同步。
- 提交消息格式：`<主题>（vX.Y.Z）`，正文写验证方式。
- 发布前把「已验证 / 未验证」写进 `docs/` 或提交正文，禁止只写「已修复」。
