## 第三轮修复（v0.3.3）—— 会话上下文族

这一批是同一个模式的集中修复：后台会话的工具链读的是全局「当前显示会话」状态。

| 位置 | 问题 | 修法 |
|---|---|---|
| 10567 `runReads` | fs-read/fs-list 的 root 取 `curWs()`（当前显示会话的工作区），后台会话会读到别的目录 | 进函数时按 `sid0` 解析 `ws0`，读、写、edit 全用它 |
| 10576 `applyEdit` | 写回用 `curWs()`，与读的目录可能不一致 | 增加 `wsIn` 参数，由调用方传 `ws0` |
| 10420 → 10607 `apply` | 自动应用传的是 `msg.id`，而 `byId()` 只查当前 `S.msgs`，后台会话永远「找不到写入申请」 | `apply` 接受消息对象，`handleTurn` 直接传 `msg` |
| 10610 `apply` 工作区 | 同样用 `curWs()` | 按 `msg.sid` 查会话工作区，取不到才回退 |
| 12216 `handleTurn`(WORK) | 判断全局 `S.cfg.mode !== 'work'`，切模式后正在跑的工具链静默停摆 | 只对「首次进入」要求 Work，已在跑的轮次不受影响 |

注意：改 `apply` 时我先把调用点改成传对象、但漏了函数签名，`byId(对象)` 会恒为 null —— 当场发现并补齐，否则所有「应用写入」都会报「找不到对应的写入申请」。

## 第四轮（v0.3.4）—— 默认直连

- `DEF_CFG.proxy` 由 `http://127.0.0.1:7897` 改为 `direct`；`direct` 是显式直连哨兵值
- 宿主 `ClientFor(proxy)`：`direct` → `DirectHttp`（`UseProxy = false`），空值仍是系统代理（原语义不变）
- 一次性迁移 `proxyDirectMigrated`：空值与旧默认 7897 都切成 `direct`，用户自己填的地址保持不动
- 诊断包显示「直连」；设置页占位符与说明同步

## 总体判断

架构本身是站得住的：单文件 + 宿主桥的分层清楚，按 sid 隔离会话、工具围栏统一解析、流式与工具链有 dead 标记防复活。问题集中在两类：

1. **后台会话与"当前显示会话"混用**（1810、7362、7466、10526、10566、12172、9772）——v2.2 引入"切走不停"之后，多处仍读全局 `S.*`，这是最容易出数据错乱的一块。
2. **异步链路上缺少"发起时快照 + 回归校验"**（7983、8276、8355、7909、7553）——等待 IO 期间用户可切会话/打字，回调却按落地时刻的状态执行。

这两类共约 12 条，占了 P1 的绝大多数。它们不是"偶发 bug"，而是同一模式在多点重复，建议下一轮集中做一次"会话上下文显式传递"的收敛改造，而不是逐条打补丁。
