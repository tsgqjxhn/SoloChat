## #1 Agent · Claude Code

**对标点**：权限模式（permission mode）。Claude Code 把权限做成三档：plan（只读规划）、default（每次询问）、acceptEdits（自动接受编辑），而不是一个「计划门禁」布尔开关。

**我们的差距**：原来只有 `planGate` 一个开关，要么「第一次写入手动确认」，要么「全自动」，没有「只读」这一档——想让它先出方案不动文件，只能靠提示词约束，靠不住。

**改动（v0.3.6）**：
- 新增 `permMode`：`ask` / `auto` / `readonly`
- 设置 → 通用设置 → 权限模式，三选一；选 `auto` 时同步把 `planGate` 置 false，兼容旧配置
- 执行端：`readonly` 时过滤掉 `fs-write` / `cmd` / `git`，写入清空并在消息里追加「🔒 只读模式：本轮 N 处写入未执行」，读类工具照跑
- 默认仍是 `ask`，行为与之前一致

**验证**：真实宿主里三态选择存在、切 `readonly` 写入 `cfg.permMode`、切 `auto` 同时关掉 `planGate`、无 JS 报错。

**没做的**：`readonly` 的端到端没有真模型回合可跑（额度未恢复），只核对了过滤逻辑与提示注入代码路径。

## #2 Chat · Claude

**对标点**：回答的耗时可见性。Claude 网页端在回复上方显示「Thought for 3s」这类耗时，用户能一眼判断是模型慢还是网络卡。

**我们的差距**：消息头部只有时间戳、token 估算，没有任何耗时信息——排查「为什么这轮这么久」只能靠猜。

**改动（v0.3.8）**：`beginStream` 记录 `t0`，`endStream` 落库时写入 `msg.ms`，消息头部按 `m.ms` 追加一栏 `3.2s`。历史消息没有该字段则不显示，不影响旧数据。

**验证**：启动无报错；语法与渲染路径核对。没跑真模型回合（额度未恢复），耗时数字的真实性待验证。

## 下一轮待办（Work 线第一个）

**目标平台**：Claude Artifacts。

**要对标的点**：产物版本历史。Artifacts 每次改动都留版本，可在侧边切换/回看；我们现在只有写入前的快照表 `SC_SNAPS`（按相对路径存、跨会话共用一格），既不能列出历史，也没有 UI。

**已确认的前置问题**（审计中发现，未修）：`SC_SNAPS` 只按相对路径做键，跨会话/跨工作区会互相覆盖，撤销可能把 A 的旧内容写进 B 的同名文件。做版本历史前必须先把它改成 `sid + 工作区 + 路径` 三元键。

**落地顺序**：
1. 快照键改三元组（数据层，先修隔离）
2. 工作区面板每个文件加「历史」入口，列出该文件的历次写入（时间 + 字节数）
3. 单条历史可预览 diff / 一键恢复

**验收**：两个会话各自写同名 `index.html`，互不干扰；恢复任一条不会影响另一会话。

**剩余**：历史列表 UI（每个文件的历次写入）、单条 diff/恢复。

## #4 Chat · ChatGPT（模型署名）

**对标点**：ChatGPT / Claude 的回答都标明是哪个模型产出的，尤其在多模型池里切换时，用户需要知道「这条是谁答的」。

**我们的差距**：消息头部只有时间、token、耗时，没有模型名。池里切来切去，历史里分不清哪条是哪个模型给的。

**改动（v0.3.21）**：收尾时把 `S.cfg.currentModel` 记进 `msg.model`；消息头部追加模型名（取 `vendor/model` 的后半段，title 里放全名）。旧消息没有该字段就不显示。

**验证**：真实宿主启动无报错、版本 `v0.3.21`。真实回答的署名要跑模型才看得到，未验证。

## #5 Agent · Cursor（Accept all）

**对标点**：Cursor 在一批待应用改动上给「Accept all / Reject all」，而不是只让用户逐条点。

**我们的差距**：一条回复里有 3 处 `fs-write`，就得点 3 次「应用写入」，顺序还得自己记住。

**改动（v0.3.23）**：消息头部在检测到 ≥2 处 `fs-write` 时出现「应用全部（N）」，一次把这条回复里的所有写入应用（同路径只算一次）；无待写入时提示而不是静默。

**验证**：真实宿主启动无报错、`FS.applyAll` 已导出、版本 `v0.3.23`。批量应用的实际落盘要真模型产出多写入回复，未验证。

## #10 Chat · ChatGPT（导出对话为 Markdown）

**对标点**：ChatGPT 能把整段对话导出成可读文件（Markdown / 文本）。

**我们的差距**：只有「完整备份」JSON（给迁移用），没有单会话的可读导出。

**改动（v0.3.35）**：新增纯函数 `chatToMarkdown(msgs, session)`（标题、导出时间、每条带角色/模型名/正文/来源），斜杠命令 `/export` 触发下载；失败消息自动跳过。

**验证**：真实宿主端到端——用三条消息（含来源与失败态）调导出函数，断言标题/正文/模型名/来源链接都在、失败消息被跳过；`/export` 在空会话只提示不发消息；无 JS 报错。

**踩的坑**：函数一开始写在 UI 内部作用域，`SC_DBG.chatMd` 引用不到（`chatToMarkdown is not defined`），移到外层才通。

## 整点提醒已暂停（重要）

原来的每小时提醒会在每次触发时开一轮完整闭环（对标 → 改代码 → 构建 → 真实宿主验证 → 发版）。目标轮次预算用尽后，它还在每小时触发，但已经没有余量做完整闭环，只能空转。

**已暂停该提醒**。恢复方式：重建一个每 3600 秒的提醒，prompt 用回原文：

> 对标时间到：打开 docs/对标记录.md，看进度表里哪种模式还没满 10 个平台（优先补齐数量最少的），从候选池里挑一个本轮没对标过的国际平台，做对标 → 落到一处具体改动 → 在真实宿主验证 → 记录到文档 → 提交并发布 0.3.x 补丁版本。不要让平台重复，版本号不要到 0.4.0。

**恢复前请先确认两件事**：① 有可用模型端点（免费额度已耗尽）；② 有新轮次预算。否则仍会重复「改完只能代码核对」的老问题。
