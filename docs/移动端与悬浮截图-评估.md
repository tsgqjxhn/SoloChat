# SoloChat 移动端与「悬浮窗截图提问」可行性评估

> 评估对象：现有 v0.5.5（单文件 `index.html` + C# WebView2 宿主）。
> 结论先行：**Android 可以做到「悬浮气泡 → 截屏 → 裁剪 → 问模型」；iOS 做不到全局悬浮窗和静默截图，只能走分享扩展/快捷指令。**

## 1. 结论

| 能力 | Android | iOS |
|---|---|---|
| 全局悬浮窗（盖在别的 App 上） | ✅ `SYSTEM_ALERT_WINDOW` + `TYPE_APPLICATION_OVERLAY`，需用户授权 | ❌ 无公开 API；PiP 只给视频，Live Activity 不是悬浮窗，AssistiveTouch 不可扩展 |
| 截取其他 App 的画面 | ✅ `MediaProjection`（每次开始投屏系统弹确认框） | ❌ 只能录/播自己的 App；`ReplayKit` 屏幕广播要用户手动开始且属直播形态 |
| 截屏后直接问 | ✅ 气泡内完成 | ✅ 但入口是「分享扩展 / 快捷指令 / 相册分享」，不是悬浮窗 |
| 后台常驻跑定时任务 | ⚠️ 前台服务 + 电池白名单，仍可能被杀 | ❌ 基本不跑；cron 不适用 |
| 上架风险 | 中（悬浮窗/投屏权限要写清用途） | 低（不碰悬浮窗） |

**推荐**：一套 Web UI（复用现有 `index.html`）→ Capacitor 壳；Android 另写悬浮窗 + MediaProjection 原生插件；iOS 只做分享扩展 + Shortcuts，不承诺悬浮窗。

## 2. 现有代码复用度

| 模块 | 手机端可行性 | 说明 |
|---|---|---|
| Chat / 公式 / 图片流 | ✅ 直接复用 | WebView 渲染，MathML 在 Android WebView / iOS WKWebView 均支持 |
| Soul 记忆（本地文件） | ✅ 复用逻辑 | 手机沙盒目录替代 `%USERPROFILE%\SoloChat\memory`；导出/导入不变 |
| 模型直连（OpenAI 兼容） | ✅ | 手机网络直连 provider；密钥进 Keystore/Keychain |
| Work 的 Python 沙箱 | ❌ | 手机没有 Python 运行时；需服务端执行或砍掉 |
| Agent 的 cmd / 本地文件工具 | ⚠️ | Android 只能访问授权目录（SAF）；iOS 仅 App 容器 |
| 内置浏览器读页面 | ⚠️ | Android WebView 可做；iOS 受限，且不能读别的 App |
| 桌面托盘通知 | ➜ 系统通知 | Android Notification / iOS UNUserNotificationCenter |
| 悬浮窗截图 | Android ✅ / iOS ❌ | 见第 4 节 |

## 3. 三种落地方案

### 方案 A：Capacitor 壳（推荐先做）
- 复用 `index.html`，用 Capacitor 打 Android/iOS 包；原生插件补：Share、Filesystem、SecureStorage、Notification、Screenshot(Android)。
- 优点：一套 UI，改动小，1–2 周能出可用包；缺点：悬浮窗要自己写 Android 插件，性能不如原生。
- 适合：先把「手机能聊天 + 记忆 + 分享图片来问」跑通。

### 方案 B：Android 原生（Kotlin + Compose）
- 悬浮气泡、MediaProjection 截屏、裁剪、OCR（ML Kit）、视觉模型流式回答全部原生。
- 优点：体验最好，悬浮窗稳定；缺点：UI 要重写一套，2–3 周 MVP，4–6 周打磨。
- 适合：确定「悬浮截图问答」是核心卖点。

### 方案 C：iOS 原生（SwiftUI + Share Extension + App Intents）
- 相册/截图 → 分享到 SoloChat → 提问；快捷指令「截屏并询问」；无悬浮窗。
- 1–2 周可做。

## 4. 悬浮截图问答的完整链路（Android）

1. **常驻气泡**：`WindowManager.addView` + `TYPE_APPLICATION_OVERLAY`，可拖动、贴边半隐、点击展开小窗。
2. **触发截屏**：点「截屏」→ 请求 `MediaProjection` 授权（系统弹窗，Android 14 起每次会话都要确认）→ `VirtualDisplay` + `ImageReader` 取一帧 Bitmap。
3. **本地预览/裁剪**：全屏半透明预览，手指框选区域；默认只发框选部分，避免把通知栏、聊天隐私带出去。
4. **可选 OCR**：ML Kit 本地识别文字，和图片一起发给模型（省 token，也让纯文本模型可用）。
5. **提问**：气泡展开小输入框 → 调多模态模型（`image_url` base64 或上传）→ 流式回答显示在气泡里；可继续追问。
6. **落记忆**：回答完可「记住这条」，写进 Soul 的 MEMORY（手机沙盒），与桌面导出格式一致。

### 权限与合规
- `SYSTEM_ALERT_WINDOW`（悬浮窗）、`FOREGROUND_SERVICE_MEDIA_PROJECTION`（投屏前台服务）、`POST_NOTIFICATIONS`。
- 商店需要说明「悬浮窗用于截图提问」；截屏内容只在用户点「发送」后上传，且明确提示会发给模型 provider。
- 支付/银行/DRM 页面系统会禁止截屏或悬浮，属正常限制，UI 要给出提示。

## 5. iOS 的替代路径

| 入口 | 体验 | 工作量 |
|---|---|---|
| 分享扩展（相册/截图分享 → SoloChat） | 选图 → 直接进提问页 | 3–5 天 |
| 快捷指令「截屏并询问」 | 截屏 → 自动打开 App 带图提问 | 2–3 天 |
| App Intents / Siri | 语音「问 SoloChat 这张图」 | 2–3 天 |
| 悬浮窗 | **平台不允许，不做** | — |

## 6. 工作量与风险

| 阶段 | 内容 | 预估 |
|---|---|---|
| Phase 0 | 响应式适配 + PWA（手机浏览器可用、可加到桌面） | 3–5 天 |
| Phase 1 | Capacitor Android/iOS 壳：聊天、模型配置、Soul 记忆、分享接收 | 2 周 |
| Phase 2 | Android 悬浮气泡 + MediaProjection + 裁剪 + 视觉问答 | 3 周 |
| Phase 3 | 跨端记忆同步（WebDAV/S3 加密）、通知/定时（WorkManager） | 1–2 周 |
| 合计 | Android 完整体验 | 6–8 周（1 人） |

**主要风险**
- 商店审核：悬浮窗 + 投屏权限要写清用途，首次上架可能被问。
- 隐私：截图可能含敏感信息 → 默认只发框选、发送前缩略图确认、不经过自建服务器。
- 密钥：必须 Keystore/Keychain，不能沿用桌面 localStorage 明文。
- 后台：Android 会杀前台服务，iOS 不允许长期后台；「定时任务」在手机上只能是「打开 App 时补跑」。
- 维护：原生壳 + Web 核心两套；用 Capacitor 把原生代码压到插件层。

## 7. 建议

1. **先 Phase 0 + Phase 1**：手机能聊天、能看图、记忆能导入导出，投入最小。
2. **Android 悬浮截图单独立项**：它是差异化点，但只对 Android 成立；先做「气泡 → 截屏 → 裁剪 → 问」最小闭环，OCR 后置。
3. **iOS 不做悬浮窗**：用分享扩展 + 快捷指令承接「截图提问」，宣传时明确平台差异。
4. 桌面端现有 `index.html` 与 Soul 文件格式不动，手机端按同一 Markdown 结构读写，保证导出可互通。
